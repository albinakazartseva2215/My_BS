# Бэкенд сервиса записи «Тон» — инженерные заметки по базе данных

Этот файл — рабочий журнал реализации бэкенда, а не архитектурный документ.
Схема — то, *что* должно быть в базе и почему, со всеми полями, типами,
ограничениями и разбором спорных решений — целиком в
[`../docs/db-schema.md`](../docs/db-schema.md). Здесь — то, *как* эта схема
реализована в коде: какой стек, какие грабли уже нашли и обошли, что нужно
для деплоя. Документ дополняется по ходу разработки, не переписывается заново.

**Если ты ИИ-ассистент, продолжающий работу в новой сессии:** прочитай сначала
этот файл целиком, потом `docs/db-schema.md`, только потом смотри код в
`src/`. Здесь собраны решения и грабли, которые иначе пришлось бы находить
заново.

## 1. Как устроена база и как это связано с логикой продукта

14 таблиц из `docs/db-schema.md` (изначально было 12 — `sessions` и
`user_roles` добавлены позже, разделы 3.3а и 3.2а), плюс служебная
`schema_migrations` (список применённых миграций, не часть предметной
области). Базовый DDL — в `src/db/migrations/001_init.sql`, дословно
скопированной из раздела 3 документа схемы; поверх неё ещё пять
миграций — `002_appointment_overlap_triggers.sql`,
`003_appointment_overlap_override.sql` (триггеры и признак осознанного
наложения, раздел 6 ниже, «Защита от двойной записи»), `004_sessions.sql`
(таблица сессий, раздел 6, «Сессии»),
`005_salon_profile_hold_duration.sql` (продуктовая настройка вместо
переменной окружения, раздел 6, «Секреты только в `.env`») и
`006_user_roles.sql` (роли списком + связь мастера с учётной записью,
раздел 6, «Роли — список, не единственное значение»). Как и `001`, все
пять дословно повторяют DDL из `docs/db-schema.md` (разделы 3.11а, 3.11б,
3.3а, 3.1а, 3.2а/3.6) — схема сначала правится в документе, потом
переносится в миграцию, не наоборот.

Ключевые связи со сценариями из паспорта продукта и карты переходов
прототипа (подробности и обоснования — в `db-schema.md`, здесь — сводка):

- **Свободного времени нет как таблицы.** Оно считается на каждый запрос
  из четырёх источников: `master_weekly_schedule` (регулярный график) →
  `schedule_exceptions` (разовые отклонения) → минус `appointments` со
  статусом `hold`/`confirmed` → минус `time_blocks`. Плюс три параметра
  из `salon_profile`: `timezone` (перевод местного графика в UTC записей),
  `booking_step_minutes` (шаг сетки слотов) и `booking_horizon_days`
  (горизонт бронирования). Ни один расчёт слотов не должен обращаться
  к какой-либо ещё таблице — если понадобилось, значит в схеме чего-то
  не хватает, а не в коде.

- **Анонимное удержание слота.** В прототипе слот придерживается на шаге
  «Дата и время» (Booking · 3), а вход/регистрация — только на следующем
  шаге. Поэтому `appointments.client_id` — nullable, а `hold_token`
  идентифицирует бронь до входа. `CHECK`-ограничение в самой таблице не
  даёт записи стать `confirmed`/`completed` без клиента. Это самое
  нетривиальное место в схеме — если меняешь логику бронирования, начни
  отсюда.

- **Защита от двойной записи** (сценарий 2 из паспорта, «состояние
  гонки») — три независимых уровня, подробности в разделе 6 ниже: явная
  проверка пересечения в коде приложения перед вставкой; частичный
  уникальный индекс `ux_appt_master_slot_active`; и триггеры БД
  `trg_appointments_no_overlap_insert`/`_update` (миграция `002`) —
  единственный уровень, который ловит пересечение диапазонов *разной*
  длительности при разных стартах, чего индекс сам по себе не может
  (SQLite не умеет range-exclusion ограничений). Осознанное наложение
  админом (`overlap_override`, миграция `003`) обходит и триггер, и
  индекс — но только в момент создания записи, не при переносе.

- **Мастера теперь МОГУТ логиниться — это пересмотр более раннего
  решения, не изначальный план.** Профиль мастера (`masters`) остаётся
  самостоятельной сущностью (не строкой в `users`) — карточка на лендинге
  живёт независимо от того, есть ли у мастера аккаунт. Но `masters.user_id`
  теперь допускает необязательную связь с пользователем, у которого роль
  `master` (`user_roles`, раздел 3.2а) — тогда он видит записи своего
  расписания через `GET /api/master/appointments`. Раньше здесь было
  «мастера не логинятся, подтверждено с постановщиком задачи явно» — это
  тоже было явное решение, и пересмотрено оно так же явно, по прямому
  новому требованию, а не тихо. Подробности и обе стороны истории — раздел
  6 ниже, «Роли — список, не единственное значение», и `docs/db-schema.md`,
  «Спорные решения», п.16.

- **Снапшоты в `appointment_services`.** Название, цена и длительность
  услуги копируются в строку записи на момент брони. Прайс меняется
  чаще, чем факт похода клиента к мастеру, — история не должна плыть
  задним числом вслед за прайсом.

## 2. Драйвер SQLite: `node:sqlite`, не `better-sqlite3`

Используется встроенный в сам Node.js модуль `node:sqlite`
(`import { DatabaseSync } from 'node:sqlite'`) — не `better-sqlite3` и не
любой другой пакет из npm. Причины:

1. **Ноль внешних зависимостей на всю базу данных.** `server/package.json`
   не содержит `dependencies` вообще. Это буквально стек «Node.js и
   SQLite» без ничего третьего.
2. **Нет риска нативной сборки.** `better-sqlite3` — нативный аддон;
   на конкретной версии Node/ОС хостинга для него может не найтись
   готового бинарника, и тогда потребуется `node-gyp` + компилятор.
   `node:sqlite` уже скомпилирован внутрь самого Node — собирать нечего.
3. **API synchronous**, как у `better-sqlite3` — `db.exec()`,
   `db.prepare(sql).run()/get()/all()`, транзакции через
   `db.exec('BEGIN')`/`COMMIT`/`ROLLBACK`. Ровно то, что нужно для
   миграций и сидов, где асинхронность только мешала бы.
4. Проверено вживую на установленной версии (Node 24.19.0): работает без
   флагов и без предупреждений об экспериментальности в stderr.

Если в будущем понадобится то, чего нет в `node:sqlite` (например,
пользовательские SQL-функции на JS или расширения SQLite), тогда стоит
пересмотреть выбор в пользу `better-sqlite3` — но добавлять его заранее,
про запас, не стали.

## 3. Нужная версия Node.js (важно для деплоя на BeGet)

**Жёсткий минимум: Node.js 22.5.0.** Модуль `node:sqlite` физически не
существует в более ранних версиях — на Node 18/20 (частый дефолт на
дешёвом виртуальном хостинге) `import('node:sqlite')` упадёт с
`ERR_MODULE_NOT_FOUND`.

Важно не путать этот порог с тем, что реально тестировалось: **22.5.0 —
это только документированный нижний порог**, ниже которого модуль
физически не существует, а не версия, на которой что-либо проверялось.
Вся разработка и все проверки в этом README фактически шли на
**Node 24.19.0** (актуальный LTS на момент написания) — именно её и
стоит ставить на BeGet, если нет отдельной причины использовать
конкретно линейку 22.x.

Что сделано, чтобы версия сервера не стала сюрпризом в момент деплоя:

- В `src/db/connection.js` — явная проверка версии перед любым
  обращением к БД. Если Node ниже 22.5.0, приложение падает сразу, с
  понятным сообщением на русском («обновите Node.js на сервере...»), а
  не с сырым стектрейсом где-то в середине запроса.
- Все npm-скрипты (`migrate`, `seed`, `db:reset`) запускают `node` с
  флагом `--experimental-sqlite`. На версиях 22.5–23.x этот флаг ещё
  обязателен; на более новых (включая 24.x) `node:sqlite` уже включён
  по умолчанию, и флаг — безопасный no-op (проверено: Node не отклоняет
  его как неизвестный).
- Если модуль всё равно не загрузился (например, кто-то запустил
  `node src/db/migrate.js` напрямую, в обход `npm run`, без флага) —
  тоже отдельное понятное сообщение с подсказкой, а не молчаливый сбой.

**Перед деплоем на BeGet:** зайти по SSH, выполнить `node --version`.
Если меньше 22.5.0 — обновить (через панель управления хостингом или
`nvm install --lts && nvm use --lts`, если есть доступ к nvm) **до**
первого запуска `npm run migrate` на сервере.

## 4. С какими сложностями столкнулись и как решили

Коротко и по делу — чтобы не наступать на те же грабли повторно.

- **`import.meta.url === 'file://' + process.argv[1]` не работает на
  Windows.** Абсолютный путь на Windows должен превращаться в
  `file:///C:/...` (три слэша), а простая конкатенация строк даёт
  `file://C:/...` (два) — сравнение никогда не совпадает, и код внутри
  `if` тихо не выполняется — без ошибки, без предупреждения. Из-за этого
  `migrate.js` сначала вообще не создавал таблицы, при этом завершался
  с кодом 0. Исправлено через `url.pathToFileURL(process.argv[1]).href`
  — это единственный надёжный способ сравнения такого рода, используйте
  его в любом новом скрипте с паттерном «выполняться только как main».

- **WAL/SHM-файлы SQLite не подпадают под маску `*.sqlite` в
  `.gitignore`.** Включили `journal_mode = WAL` — рядом с
  `database.sqlite` появляются `database.sqlite-wal` и
  `database.sqlite-shm`, у которых расширение не `.sqlite`, а
  `.sqlite-wal`/`.sqlite-shm`. Общие маски их не ловят. Решение — не
  городить ещё маски, а просто добавить в `.gitignore` весь каталог
  целиком: `/server/data/`.

- **Неизвестная версия Node.js на проде (BeGet).** См. раздел 3 —
  решили явной проверкой версии в коде плюс защитным флагом
  `--experimental-sqlite` во всех npm-скриптах, а не предположением,
  что на сервере окажется «достаточно новый» Node.

- **Момент создания записи не совпадает с моментом входа клиента.**
  При повторном разборе карты переходов прототипа обнаружилось: слот
  придерживается на шаге 3 («Дата и время»), а вход/регистрация — только
  на шаге 4. Первая версия схемы требовала `client_id NOT NULL`, что
  физически не соответствовало этому порядку экранов. Решение —
  `client_id` nullable + `hold_token` для анонимной идентификации до
  входа, подробный разбор альтернатив — в `docs/db-schema.md`, раздел
  «Спорные решения», пункт 12.

- **«Мастер» — не то же самое, что «пользователь с ролью мастер» — но это
  больше не значит «мастер не может залогиниться».** Формулировка задачи
  на сид тестовых данных изначально подразумевала три роли
  (админ/мастер/клиент), и первая версия схемы развела это на `users`
  (логин, `client`/`admin`) и `masters` (профиль без входа) — решение
  подтвердили с постановщиком задачи явно. Это решение с тех пор
  пересмотрено — тоже явно, по прямому запросу того же постановщика
  задачи («роли списком, мастер и админ одновременно», «мастер видит
  записи своего расписания») — см. раздел 6 ниже. Оставшаяся часть
  прежнего рассуждения не изменилась: `masters` по-прежнему отдельная от
  `users` сущность (профиль без логина остаётся легальным состоянием),
  просто связь между ними теперь может существовать (`masters.user_id`).

- **Хеширование пароля без внешних зависимостей.** Вместо `bcrypt`/
  `argon2` — встроенный `node:crypto` (`scryptSync` + `timingSafeEqual`),
  вынесено в `src/security/passwords.js`. `bcrypt`/`argon2` осознанно не
  рассматривались: у обоих нативные (C++) сборки, которые на сервере
  могут не собраться без компилятора/`node-gyp` — тот же риск, из-за
  которого для БД выбран `node:sqlite`, а не `better-sqlite3` (раздел 2).
  Соль — случайная, своя для каждого пароля. Формат хранимого значения —
  `scrypt:<N>:<r>:<p>:<keylen>:<соль-hex>:<хеш-hex>`: параметры стойкости
  (`N`/`r`/`p`) и длина ключа хранятся прямо в строке, а не берутся из
  текущих констант модуля — иначе смена дефолтов для новых паролей в
  будущем сделала бы непроверяемыми уже сохранённые хеши (`verifyPassword`
  обязан пересчитывать scrypt с теми же параметрами, с которыми хеш
  создавался, а взять их неоткуда, кроме самой строки). Тот же модуль
  используется и в `seed.js` (тестовые пользователи), и в API
  аутентификации (`routes/auth.routes.js`, `domain/passwordReset.js`) —
  единственное место, где вообще должен упоминаться пароль в открытом виде.

- **Идемпотентность сида без ORM/upsert-логики.** `src/db/seed.js`
  просто удаляет управляемые им таблицы целиком и заново вставляет
  данные внутри одной транзакции — проще, чем возиться с `UPSERT`, и
  для dev-сида этого достаточно. Пока в проекте нет API регистрации,
  сиду разрешено удалять всю таблицу `users` целиком; как только
  появится реальная регистрация, это нужно будет сузить до «удалять
  только тестовых пользователей по email», иначе сид на дев-окружении
  будет стирать чужие тестовые аккаунты.

- **Правка одной защиты от двойной записи — не повод забыть остальные.**
  При добавлении `overlap_override` (миграция `003`) сначала поправили
  только триггер `trg_appointments_no_overlap_insert`, забыв, что
  `ux_appt_master_slot_active` — отдельный, самостоятельный механизм
  (раздел 6). Админ с `overlapOverride: true` получал не `201`, а те же
  `409` — ровно на самом частом случае наложения (совпадение времени
  старта), потому что индекс останавливал вставку раньше, чем до неё
  вообще доходило дело до триггера. Нашлось не чтением кода, а прогоном
  запроса через реальный HTTP API. Урок: когда «одна и та же гарантия»
  на самом деле реализована в нескольких независимых местах (индекс И
  триггер — оба про пересечение слотов, но разные механизмы БД), правка
  одного не гарантирует, что другой не откатит её эффект — проверять
  нужно результат сквозного запроса, а не то, что «нужный» кусок кода
  поправлен. Подробности — `docs/db-schema.md`, «Спорные решения», п.13.

- **Слоты свободного времени видимо «перекрываются» — это не баг, а
  независимость шага сетки от длительности услуги.** Нашлось при
  тестировании фронтенда: `GET /api/masters/:id/availability` для
  мастера с `booking_step_minutes = 60` и выбранными услугами на 65
  минут суммарно честно отдаёт слоты `10:00–11:05`, `11:00–12:05` и
  т. д. — соседние кандидаты пересекаются на несколько минут. Так и
  задумано (`domain/availability.js`, `computeAvailableSlots`): шаг
  сетки и длительность услуги — независимые параметры, кандидаты на
  старт ставятся каждые `booking_step_minutes` минут вне зависимости от
  того, сколько займёт сама услуга. Список слотов — это набор
  допустимых времён СТАРТА, а не гарантированно совместимых друг с
  другом окон; занять можно только один из перекрывающихся вариантов —
  проверено вживую: после бронирования `10:00` слот `11:00` (пересекался
  с ним) тут же пропадает из списка на следующий запрос, а
  непересекающиеся остаются. Если это когда-нибудь понадобится изменить
  (например, чтобы кандидаты никогда не перекрывались) — это
  осознанное продуктовое решение про шаг сетки, а не починка бага.

- **`GET /api/masters/:id/availability` стал отдавать `allSlots` —
  занятые старты, не только свободные.** Понадобилось при вёрстке
  Booking · 3: экран должен показывать занятое время в сетке видимым и
  неактивным (серая перечёркнутая кнопка среди свободных), а не молча
  прятать — но `slots` всегда был списком только свободных стартов.
  Фронт не может сам восстановить, какие именно часы заняты, а какие
  мастер просто не работает: и то, и другое выглядит одинаково —
  отсутствием в `slots`, а границы рабочего окна на день и шаг сетки
  (`booking_step_minutes`) наружу не отдавались вообще. Решение —
  аддитивное: `computeAvailableSlots` (`domain/availability.js`) считает
  тот же перебор кандидатов старта, что и раньше, но теперь помечает
  каждого статусом `free`/`busy`/`past` и отдаёт всех через `allSlots`;
  `slots` при этом не менялся ни по составу, ни по формату — только
  свободные, не прошедшие старты, как и раньше (`frontend/public/
  availability.html` как читал `data.slots`, так и продолжит). Кандидаты,
  для которых выбранная длительность вообще не помещается до закрытия,
  как не участвовали в переборе, так и не участвуют — грид не притворяется,
  что показывает «все часы работы», только те старты, куда услуга
  физически влезает (тот же смысл, что и в тексте на самом экране:
  «показываем только подходящие окна»).

## 5. Команды и карта файлов

Все команды — из папки `server/`:

```bash
npm run migrate    # применяет ещё не применённые миграции из src/db/migrations/
npm run db:reset   # удаляет файл БД (и -wal/-shm) и накатывает миграции с нуля
npm run seed       # наполняет базу тестовыми данными (идемпотентно)
```

`db:reset` и `seed` отказываются выполняться при `NODE_ENV=production` —
это защита от случайного запуска dev-скрипта на боевом сервере, а не
формальность.

```
server/
├── README.md                    # этот файл
├── .env.example                 # список нужных переменных окружения (реальный .env — в .gitignore)

## 6. HTTP API — как устроен код в `src/`

API написан поверх `node:http` без фреймворка (без express) — тот же
принцип «ничего третьего», что и у слоя БД (раздел 2). Свой роутер —
`src/http/router.js`, статические сегменты и `:param`, без regex-магии
сверх необходимого.

Карта файлов:

```

│                                  пользователь из сессии + единая обработка ошибок

│                                  раз в минуту (истёкшие hold, прошедшие визиты)

│                                  начале каждого маршрута, до обращения к БД

**Сессии — теперь с таблицей в БД (`sessions`, `docs/db-schema.md`,
раздел 3.3а).** Первая версия обходилась без неё: подписанный (HMAC)
токен без состояния на сервере, срок действия проверялся по подписи, а
`logout` мог только снять cookie — сам токен, если его успели
скопировать, оставался действителен до истечения TTL. Решение было
осознанным на тот момент («заводить таблицу в обход документа —
менять схему по ходу задачи»), но прямое требование — ограниченный срок
действия токена и хранение его хеша, а не самого токена — вместе
физически нельзя выполнить без строки в базе, так что решение
пересмотрено, а не обойдено (разбор — `docs/db-schema.md`, «Спорные
решения», п.14).

Как это устроено сейчас: `POST /api/auth/login` создаёт строку в
`sessions` (`domain/session.js`, `createSession`) — `expires_at = now +
SESSION_TTL_DAYS`, `token_hash` — HMAC-SHA256 от токена с ключом
`SESSION_SECRET` (`.env`, см. `.env.example`); сам токен возвращается
клиенту ровно один раз и больше нигде не хранится, только в httpOnly-
cookie. Каждый аутентифицированный запрос (`middleware/auth.js`,
`resolveCurrentUser`) хешируeт предъявленный токен и ищет действующую
(не отозванную, не истёкшую) строку по хешу. `POST /api/auth/logout`
теперь помечает сессию `revoked_at` по-настоящему — не только снимает
cookie: тот же токен, предъявленный вручную после logout (не через
cookie-jar браузера, а напрямую в заголовке), получает `401` —
проверено вживую. Строки не удаляются физически (тот же принцип, что и
у `appointments`/`password_reset_tokens`) — история входов остаётся.

**Деньги — рубли, не копейки.** Сохранено ровно так, как в
`docs/db-schema.md` («Спорные решения», п.4): `price_rub` и производные
поля — целые рубли. API отдаёт и принимает суммы в тех же целых рублях
(поле называется `priceRub`), без домножения на 100 — намеренно, чтобы
не создавать формат, которого нет в хранимых данных.

**Защита от двойной записи** реализована в два слоя, как и предписано
документом схемы (раздел 4, «Спорные решения» п.1): явная проверка
пересечения диапазона в `src/domain/availability.js` внутри транзакции
`BEGIN IMMEDIATE` (см. `runOverlapProtectedInsert` в `booking.js`), и
частичный уникальный индекс `ux_appt_master_slot_active` — как
подстраховка на случай гонки за точное совпадение времени старта.
`node:sqlite` синхронный, поэтому между `BEGIN IMMEDIATE` и `COMMIT` в
коде нет ни одного `await` — событийный цикл Node физически не может
впустить туда параллельный запрос в рамках одного процесса.

**«Удаление» истёкших удержаний** (требование задачи) реализовано как
`status = 'expired'`, а не физический `DELETE FROM appointments` —
строки сознательно остаются для истории, это прямо описано в
`docs/db-schema.md` («Спорные решения», п.10). Смены статуса достаточно:
частичный уникальный индекс на слот действует только для
`hold`/`confirmed`, поэтому «удаление» здесь — это освобождение слота
для новой брони, а не стирание строки. Зачистка — лениво перед каждым
расчётом свободного времени/созданием брони, и дополнительно раз в
минуту фоновым таймером в `index.js`.

**CORS осознанно не настроен — фронтенд появился, но обошёлся без него.**
Когда этот абзац писался впервые, здесь стояло «фронтенда пока нет,
настраивать не под кого». Фронтенд (`frontend/`) появился (раздел «Дальше
по проекту» ниже), но `Access-Control-Allow-Origin` и подобные заголовки
в `server/` по-прежнему не добавлены — не забыто, а не понадобилось:
`frontend/server.js` — свой маленький dev-сервер, который раздаёт статику
И проксирует `/api/*` на этот бэкенд. Браузер в результате видит один и
тот же origin (`http://localhost:5173`) что для страниц, что для API —
CORS просто не в игре, а заодно сессионная cookie (`HttpOnly`,
`SameSite=Lax`, без `Secure` в деве) работает как есть, без единой правки
здесь. Если у фронтенда когда-нибудь появится собственный домен без
прокси перед этим API — вот тогда вернуться к этому абзацу и настроить
`Access-Control-Allow-Origin` под конкретный origin.

**Восстановление пароля** (`domain/passwordReset.js`,
`POST /api/auth/password-reset/request` и `/confirm`) — реализовано
позже остального API, отдельным заходом: паспорт продукта прямо называет
эту функцию («Функция 1 … включая восстановление пароля»), но в
прототипе для неё нет экрана (`docs/db-schema.md`, «Спорные решения»,
п.8) — таблица `password_reset_tokens` была заведена заранее, логики не
было. Токен хешируется тем же способом, что и пароль пользователя
(`security/passwords.js`, scrypt) — искать его по значению напрямую
нельзя (хеш с солью не детерминирован), поэтому `confirm` принимает
`email` + `token` и ищет действующий токен по пользователю, а не по хешу
сразу. Одна проблема нашлась не в коде, а в самом паспорте: «Уведомления
приходят только внутри личного кабинета, интеграция с e-mail или
Telegram не входит в MVP» — а восстановление пароля по смыслу требует
канала **вне** личного кабинета (иначе замкнутый круг: чтобы увидеть
ссылку сброса, нужно быть залогинен). Решение, принятое явно с
постановщиком задачи: на время MVP `POST .../request` возвращает токен
прямо в теле ответа, а не отправляет его по почте — так функцию вообще
можно проверить и использовать без email-интеграции. Это осознанный
компромисс, а не то, как это должно работать в проде: токен в ответе
превращает «знание e-mail» в «может сбросить пароль этого аккаунта»,
теряя подтверждение владения почтой.

**Обновление по итогам проверки безопасности (см. также раздел «Ещё один
аудит» ниже):** пока это было чисто теоретическим описанием риска, `resetToken`
отдавался в ответе всегда, независимо от окружения. Живая проверка
подтвердила, что это не гипотетический, а рабочий вектор захвата чужого
аккаунта — зная только e-mail любого пользователя (в т.ч. из seed-данных),
можно было получить действующий токен сброса и один запрос `/confirm`
спустя знать новый пароль чужого аккаунта, не зная старого. Плюс сам
маршрут `/request` не был ограничен по частоте (`middleware/rateLimit.js`
раньше знал только про `login`/`register`) — то есть e-mail-адреса можно
было перебирать без ограничения скорости.

Исправлено без ожидания email/Telegram-интеграции (по прямому запросу —
токен в проде важнее оставить недоступным сейчас, чем ждать, пока
появится канал доставки): `resetToken`/`expiresAt` теперь попадают в ответ
`POST /api/auth/password-reset/request` только при `!env.isProduction`
(`routes/auth.routes.js`) — тот же приём, что уже применяется к
`db:reset`/`seed` (раздел 3 выше): то, что нельзя безопасно включить без
ещё не реализованной части (настоящая отправка письма), не изображает
готовую фичу в production, а честно не работает до тех пор, пока эта
часть не появится. В разработке (`NODE_ENV=development`/`test`, то есть
везде, где сейчас идёт работа над проектом) поведение не изменилось —
токен по-прежнему в ответе, функцию всё так же можно проверять и
использовать без email-интеграции. Плюс оба маршрута
(`password-reset/request` и `/confirm`) добавлены в `ROUTE_LIMITS`
(5 и 10 запросов за 15 минут на IP — как у `register`/`login`
соответственно).

Когда появится реальная email/Telegram-интеграция: отправлять токен по
каналу вместо (не вместе с) возврата в ответе, и тогда же можно убрать
условие `!env.isProduction` совсем — хранение и проверку самого токена
трогать не придётся, меняется только то, куда токен попадает после
выпуска.

**Завершённые визиты и категории услуг** — закрывали не по прямому
запросу на фичу, а по собственному списку «осталось за рамками задачи»,
поэтому стоит явно пояснить, откуда они взялись:

- `status = 'completed'` теперь выставляется двумя путями — сразу оба, а
  не один на выбор, потому что документ схемы (`docs/db-schema.md`,
  раздел 6) описывает их через «или», не «либо-либо»: `POST
  /api/admin/appointments/:id/complete` (ручной, когда админу нужно
  закрыть визит раньше или без ожидания фоновой задачи) и
  `completePastAppointments` (`domain/completionSweep.js`) — тот же
  принцип ленивой зачистки, что и у `releaseExpiredHolds`: перед выдачей
  `GET /api/admin/appointments` и дополнительно раз в минуту фоновым
  таймером в `index.js`. На расчёт свободного времени смена `confirmed`
  → `completed` не влияет (прошедшие слоты и так не предлагаются) — это
  только гигиена данных для админ-панели.
- `service_categories` получили CRUD (`GET/POST/PATCH
  /api/admin/service-categories`) — раньше наполнялись только через
  `npm run seed`, и админ не мог завести новую категорию для новой
  услуги, не трогая код. Без hard-`DELETE` — как и у услуг/мастеров,
  сознательно только создание/переименование, потому что категория,
  на которую уже ссылаются услуги, не может быть физически удалена без
  `ON DELETE CASCADE`, которого в схеме нет намеренно (см.
  `docs/db-schema.md`, `services.category_id`).

**Секреты только в `.env`, продуктовые настройки — только в БД.** По
прямому запросу прогнали весь `src/` на предмет ключей/паролей,
зашитых в код (`grep` по `process.env.` — читается только в
`config/env.js`, больше нигде; отдельный `grep` на литералы вида
`apiKey`/`secretKey`/`-----BEGIN` — пусто) и на то, не оказалась ли
какая-то продуктовая настройка по ошибке в `.env` вместо БД. Нашлась
одна: `HOLD_DURATION_MINUTES` (длительность удержания слота) была
переменной окружения, хотя по тому же рассуждению, что и уже
существующие `booking_step_minutes`/`booking_horizon_days` в
`salon_profile`, — это продуктовое решение о бронировании, которое
администратор салона должен мочь поменять сам, а не секрет и не
инфраструктура. Перенесено в `salon_profile.hold_duration_minutes`
(миграция `005_salon_profile_hold_duration.sql`); заодно добавлены
`GET`/`PATCH /api/admin/salon-profile` — раньше `salon_profile` вообще
нельзя было прочитать или поменять через API, только через `npm run
seed`/прямой доступ к БД, хотя таблица для этого и создавалась.
`SESSION_TTL_DAYS`/`PASSWORD_RESET_TTL_MINUTES` в `.env` остались —
это параметры безопасности (срок жизни токена входа/сброса пароля),
решение уровня разработки/эксплуатации, не то, что крутит через
настройки продукта нетехнический владелец салона. Проверено вживую:
без роли админа `GET /api/admin/salon-profile` — `401`; невалидный
часовой пояс в `PATCH` — `400`; изменение `holdDurationMinutes` через
API реально меняет, через сколько минут истекает новое удержание слота
(`POST /api/holds`) — не через отдельный деплой `.env`.

**Роли — список, не единственное значение; мастер может логиниться и видеть своё расписание.** Прямой пересмотр решения из раздела 1 выше и `docs/db-schema.md`, «Спорные решения», п.16 — там же полная история «было/стало». Здесь — что именно поменялось в коде:

- `user_roles(user_id, role)` вместо `users.role` (миграция `006_user_roles.sql`, данные перенесены, колонка `role` физически удалена — `ALTER TABLE ... DROP COLUMN`, `node:sqlite` это умеет). `db/repositories/users.js`: `listRolesForUser`/`findUserWithRolesById`/`findUserWithRolesByEmail`/`grantRole`/`revokeRole`; `toPublicUser` теперь требует `row.roles` (массив) и намеренно бросает исключение, если его забыли подгрузить, а не тихо подставляет `[]`.
- `middleware/auth.js`: `requireRole(ctx, role)` теперь `!user.roles.includes(role)`, не `user.role !== role` — сигнатура вызова не изменилась, поэтому все существующие `requireRole(ctx, 'admin')` в `admin.routes.js` не пришлось трогать. Добавлен `requireAnyRole(ctx, roles)` — для точек входа, доступных нескольким ролям сразу (пока не используется, оставлен для следующего такого случая).
- **Три проверки на каждом эндпоинте с записями** (`routes/appointments.routes.js`) — авторизован → есть подходящая роль → принадлежит ли объект. Раньше было бинарно (`assertOwnerOrAdmin`), теперь два варианта: `assertCanAccessAppointment` (чтение — `admin` видит всё, `client` — где он клиент, `master` — где `master_id` совпадает с профилем по `masters.user_id`) и более узкий `assertCanModifyAppointment` (перенос/отмена — только `admin` или `client`-владелец; `master` намеренно не допущен — запрос говорил «видит», не «меняет», расширять молча не стали). Новый `routes/master.routes.js` → `GET /api/master/appointments` — список своего расписания, требует роль `master` и привязанный профиль (403 с понятным текстом, если роль есть, а профиль не привязан — не пустой список молча).
- Управление ролями и привязкой — только у админа: `POST/DELETE /api/admin/users/:id/roles[/:role]` (выдать/отозвать `admin`/`master`; `client` не входит в список — выдаётся только при регистрации и не отзывается через этот эндпоинт; нельзя отозвать единственную оставшуюся роль — `400`, защита от опечатки, оставляющей аккаунт вообще без единой роли) и `PATCH /api/admin/masters/:id` — новое поле `userId` (`null` отвязывает, число — привязывает и заодно выдаёт роль `master`, инвариант «привязан ⇒ есть роль» держит код, не `CHECK`, SQLite не умеет кросс-табличные ограничения).
- **Баг, найденный вручную при проверке привязки.** Первая версия `PATCH .../masters/:id` с `userId` проверяла только «этот пользователь ещё не привязан к другому мастеру» — но не «этот профиль мастера ещё не привязан к другому пользователю». Итог: `PATCH /api/admin/masters/2 {"userId": 2}`, когда master id=2 уже был привязан к user_id=4 (Полина, её собственный логин), тихо переписывал привязку на постороннего клиента — `200`, без единой ошибки, и Полина в этот момент теряла доступ к своему же расписанию (`findMasterByUserId(4)` перестал бы что-либо находить), а чужой клиент внезапно получал бы её данные через `GET /api/master/appointments`. Нашлось не чтением кода, а прогоном ровно этого сценария через реальный API — то же самое, чем нашлись баги в п.13/14 `docs/db-schema.md`: ручная проверка сценария с реальными данными, а не вычитывание диффа. Исправлено проверкой обеих сторон связи; попытка молча переподвязать занятый профиль теперь `409` с объяснением («сначала отвяжите»), а не тихая кража доступа.
- `seed.js`: два новых демо-логина — `anna.master@ton-salon.test` (только роль `master`, привязан к профилю «Анна Соколова») и `polina.masteradmin@ton-salon.test` (`master` + `admin` одновременно, привязан к «Полина Ерохина») — ровно тот пример множественных ролей, который просили показать явно, не только описать.

Проверено вживую: `POST /api/auth/login` для всех четырёх демо-аккаунтов отдаёт `roles` списком (у Полины — `["admin","master"]`); Анна видит `GET /api/master/appointments` (`200`, свои записи с данными клиента), получает `403` на `/api/admin/appointments`; обычный клиент получает `403` на `/api/master/appointments`; Анна получает `403` при попытке посмотреть запись из расписания Полины и при попытке отменить свою же запись (мастеру только чтение); Полина (обе роли) проходит и `/api/master/appointments`, и `/api/admin/appointments`; выдача/отзыв ролей и защита «последней роли» — `200`/`400` как задумано; описанный выше баг с привязкой — воспроизведён, исправлен, повторно проверен (`409` вместо тихой кражи, явная последовательность отвязать→привязать даёт `200`).

**Ещё один аудит по прямому запросу — параметризация, вход пользователя, ограничение частоты, утечка внутренних деталей в ошибках.** Прогнал и задокументировал по всем четырём пунктам:

- **Параметризация SQL.** Перечитал каждый `db.prepare`/`db.exec` во всём `src/` (не только `db/repositories/`, но и `domain/*.js`, где тоже есть прямые запросы). Везде, где в SQL-текст через `${...}` попадает что-то динамическое — это либо список колонок из жёстко заданного массива `[key, column]` пар (никогда не ключ из пользовательского объекта напрямую), либо строка `?,?,?` для `IN (...)`, сгенerированная по количеству элементов. Само значение всегда уходит через `?` в `.run()`/`.get()`/`.all()`. Проверил вживую: имя при регистрации `Robert'; DROP TABLE users; --` сохранилось как обычный текст, таблица `users` цела.
- **Валидация входа — нашёл и закрыл два реальных пробела.** (1) `DELETE /api/holds/:holdToken` брал параметр из URL без проверки типа/длины — исправлено, `requireString` с ограничением длины. (2) `requireUtcDateTime` (`validation/validate.js`) принимал математически некорректные даты — `new Date('2026-02-30...')` в JS не бросает исключение и не даёт `NaN`, а молча "перекатывает" 30 февраля в 2 марта; `isNaN(...)` при этом `false`. Переписано на явный `Date.UTC()` + round-trip-проверку (тот же приём, что уже был в `requireDateString`, просто не был перенесён на datetime) — теперь несуществующая дата/время в `startDatetime`/`endDatetime` даёт `400`, а не тихо подставленную "соседнюю" дату. Поля, которые пользователь не может задавать сам (`role` при регистрации, `client_id`/`status`/`overlapOverride` при создании записи не-админом), нигде не читаются из тела запроса на клиентских маршрутах вообще — не "отклоняются", а физически отсутствуют в коде, который эти маршруты выполняет (см. `domain/booking.js`, `createAppointment` — `overlapOverride` туда прокидывает только `routes/admin.routes.js`, после `requireRole`).
- **Ограничение частоты запросов** (`middleware/rateLimit.js`) — раньше не было вовсе. Вход и регистрация лимитируются раздельно (10 и 5 запросов за 15 минут на IP+маршрут соответственно — регистрацию лимитировал жёстче, там частые легитимные повторы маловероятны, а спам-риск выше). В памяти процесса, не в БД и не в Redis — тот же принцип "ничего третьего", что и у остального бэкенда; оборотная сторона — счётчики не переживают перезапуск и не разделяются между несколькими инстансами, если сервис когда-нибудь станет кластером. IP — из `req.socket.remoteAddress`, не из `X-Forwarded-For` (сервис не задекларирован как стоящий за реверс-прокси, а слепо доверять этому заголовку — значит дать любому обойти лимит). Зачистка старых окон — по тому же таймеру в `index.js`, что и `releaseExpiredHolds`/`completePastAppointments`. Проверено вживую: 429 с заголовком `Retry-After` после превышения лимита.
- **Внутренние подробности в ошибках** — уже было закрыто архитектурно, отдельно ничего чинить не пришлось: `app.js` перехватывает исключения в одном месте (`requestListener`), и только `ApiError` (все сообщения которого написаны руками, вручную) отдаёт `.message` клиенту — любая другая ошибка (SQL, файловая система, что угодно) уходит в `console.error` на сервере и превращается в фиксированный `"Внутренняя ошибка сервера"`. Отдельно проверил `grep`-ом по всему `src/`, что нигде текст пойманного исключения (`err.message`/`e.message`) не передаётся ни в один из `badRequest`/`conflict`/... — пусто.

**Ещё один аудит, уже в рамках подготовки фронтенда (`frontend/`, см. «Дальше по проекту» ниже) — IDOR через подстановку ID, обход проверки роли, пароли/ключи в коде, непараметризованные запросы, отсутствие валидации входа.** Пять конкретных пунктов, каждый — не только чтением кода, но и живыми запросами к работающему API:

- **IDOR по записям** — вошёл под одним клиентом, дёргал `GET/PATCH/POST /api/appointments/:id` чужих записей и как неавторизованный. Доступ везде корректно закрыт (`assertCanAccessAppointment`/`assertCanModifyAppointment`, `routes/appointments.routes.js`). Побочный эффект, который стоит иметь в виду, не обязательно чинить: ответ на чужую запись — `403`, на несуществующую — `404`, так что авторизованный пользователь может перебором ID узнать, какие ID вообще существуют (не их содержимое).
- **Обход роли** — поддельный `Bearer`-токен, битый `session`-cookie, клиент на `/api/admin/*` и `/api/master/appointments`, `role`/`roles` в теле регистрации, `overlapOverride`/`status`/`clientId` в теле клиентского бронирования, `masterId` при переносе не-админом. Везде корректно `401`/`403`/`400` — привилегированные поля физически не читаются из тела на клиентских маршрутах (см. тот же вывод в пункте про валидацию выше), подделать нечем.
- **Секреты в коде** — независимо повторил `grep` по `apiKey`/`secretKey`/`password\s*=`/`-----BEGIN` по всему `src/`; единственное срабатывание — тестовые пароли демо-аккаунтов в `db/seed.js` (уже описаны там же и в этом README, `seed` не запускается при `NODE_ENV=production`). `.env` не закоммичен, в репозитории только `.env.example`.
- **Непараметризованные запросы** — тот же вывод, что и в предыдущем аудите выше, плюс живая проверка: `Robert'; DROP TABLE users; --` в `name` при регистрации и `'); DROP TABLE appointments; --` в `comment` записи сохранились как обычный текст, таблицы целы, вход продолжил работать.
- **Валидация входа** — пустое тело, битый e-mail, `masterId` не числом, `serviceIds` с мусором, тело-массив/строка вместо объекта, битый JSON — везде понятный `400` через `validate.js`/`readJsonBody`. Нашёл один пробел, не закрыт: `photoUrl` у мастера (`admin.routes.js`, `POST/PATCH /api/admin/masters`) принимает любую строку без проверки схемы — `javascript:alert(...)` сохраняется как есть. Сам API это значение никак не исполняет и не рендерит, поэтому здесь это не уязвимость API, а потенциальный риск для будущего фронтенда, если тот когда-нибудь отрендерит `photoUrl` как `<img src>` без экранирования.

Из пяти пунктов — реальная, не гипотетическая проблема нашлась в шестом, смежном: **восстановление пароля**. Живой запрос `POST /api/auth/password-reset/request` с чужим e-mail (`client@ton-salon.test`, без знания его пароля) отдавал рабочий `resetToken` — то есть само по себе знание чужого e-mail превращалось в полный захват аккаунта, а сам маршрут вдобавок не был ограничен по частоте. Это тот самый компромисс MVP из абзаца «Восстановление пароля» выше — но проверка показала, что от компромисса до рабочей дыры расстояние было куда меньше, чем можно было бы подумать по одному описанию в README. Исправлено: `resetToken` теперь в ответе только при `!env.isProduction`, `password-reset/request`/`/confirm` добавлены в `ROUTE_LIMITS` — подробности и вживую проверенное поведение (dev vs production, полный цикл запрос→подтверждение→вход) — в абзаце «Восстановление пароля» выше, там же, где был описан исходный компромисс, а не в новом месте.

- Восстановление пароля не работает целиком в `NODE_ENV=production` —
  `resetToken` там больше не возвращается в ответе API (см. абзац

  нужно добавить саму отправку и убрать условие `!env.isProduction`

Пункты «фронтенда нет» и «CORS не настроен», которые раньше стояли здесь

`Access-Control-Allow-Origin` не для чего (подробнее — абзац «CORS

появится собственный домен без прокси перед бэкендом — вот тогда этот

(`docs/db-schema.md`, 3.3а; `domain/session.js`) появилась по прямому
требованию к API (ограниченный срок действия токена + хранение хеша, а
не самого токена), см. раздел 6 выше. Проверено вживую: `logout`
реально отзывает сессию — тот же токен, предъявленный после logout,
получает `401`, а не только теряет cookie у браузера.

этого файла, не создавайте по новому документу на каждую фичу.
