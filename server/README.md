# Бэкенд сервиса записи «Тон» — инженерные заметки по базе данных

Этот файл — рабочий журнал реализации бэкенда, а не архитектурный документ.
Схема — то, *что* должно быть в базе и почему, со всеми полями, типами,
ограничениями и разбором спорных решений — целиком в
[`../docs/db-schema.md`](../docs/db-schema.md). Здесь — то, *как* эта схема
реализована в коде: какой стек, какие грабли уже нашли и обошли, что нужно
для деплоя. Документ дополняется по ходу разработки, не переписывается заново.

**Если ты ИИ-ассистент, продолжающий работу в новой сессии:** прочитай сначала
этот файл целиком, потом `docs/db-schema.md`, только потом смотри код в
`src/`. Здесь собраны решения и грабли, которые иначе пришлось бы находить
заново.

## 1. Как устроена база и как это связано с логикой продукта

12 таблиц из `docs/db-schema.md`, плюс служебная `schema_migrations`
(список применённых миграций, не часть предметной области). Базовый
DDL — в `src/db/migrations/001_init.sql`, дословно скопированной из
раздела 3 документа схемы; поверх неё ещё две миграции —
`002_appointment_overlap_triggers.sql` и
`003_appointment_overlap_override.sql` — добавили триггеры и признак
осознанного наложения (раздел 6 ниже, «Защита от двойной записи»). Как и
`001`, обе дословно повторяют DDL из `docs/db-schema.md` (разделы 3.11а
и 3.11б) — схема сначала правится в документе, потом переносится в
миграцию, не наоборот.

Ключевые связи со сценариями из паспорта продукта и карты переходов
прототипа (подробности и обоснования — в `db-schema.md`, здесь — сводка):

- **Свободного времени нет как таблицы.** Оно считается на каждый запрос
  из четырёх источников: `master_weekly_schedule` (регулярный график) →
  `schedule_exceptions` (разовые отклонения) → минус `appointments` со
  статусом `hold`/`confirmed` → минус `time_blocks`. Плюс три параметра
  из `salon_profile`: `timezone` (перевод местного графика в UTC записей),
  `booking_step_minutes` (шаг сетки слотов) и `booking_horizon_days`
  (горизонт бронирования). Ни один расчёт слотов не должен обращаться
  к какой-либо ещё таблице — если понадобилось, значит в схеме чего-то
  не хватает, а не в коде.

- **Анонимное удержание слота.** В прототипе слот придерживается на шаге
  «Дата и время» (Booking · 3), а вход/регистрация — только на следующем
  шаге. Поэтому `appointments.client_id` — nullable, а `hold_token`
  идентифицирует бронь до входа. `CHECK`-ограничение в самой таблице не
  даёт записи стать `confirmed`/`completed` без клиента. Это самое
  нетривиальное место в схеме — если меняешь логику бронирования, начни
  отсюда.

- **Защита от двойной записи** (сценарий 2 из паспорта, «состояние
  гонки») — три независимых уровня, подробности в разделе 6 ниже: явная
  проверка пересечения в коде приложения перед вставкой; частичный
  уникальный индекс `ux_appt_master_slot_active`; и триггеры БД
  `trg_appointments_no_overlap_insert`/`_update` (миграция `002`) —
  единственный уровень, который ловит пересечение диапазонов *разной*
  длительности при разных стартах, чего индекс сам по себе не может
  (SQLite не умеет range-exclusion ограничений). Осознанное наложение
  админом (`overlap_override`, миграция `003`) обходит и триггер, и
  индекс — но только в момент создания записи, не при переносе.

- **Мастера не логинятся.** `users.role` — только `client`/`admin`.
  Профиль мастера (`masters`) — самостоятельная сущность без пароля и
  входа; управляется администратором. Это осознанное решение, принято
  явно (не додумано молча) — см. раздел 4 ниже.

- **Снапшоты в `appointment_services`.** Название, цена и длительность
  услуги копируются в строку записи на момент брони. Прайс меняется
  чаще, чем факт похода клиента к мастеру, — история не должна плыть
  задним числом вслед за прайсом.

## 2. Драйвер SQLite: `node:sqlite`, не `better-sqlite3`

Используется встроенный в сам Node.js модуль `node:sqlite`
(`import { DatabaseSync } from 'node:sqlite'`) — не `better-sqlite3` и не
любой другой пакет из npm. Причины:

1. **Ноль внешних зависимостей на всю базу данных.** `server/package.json`
   не содержит `dependencies` вообще. Это буквально стек «Node.js и
   SQLite» без ничего третьего.
2. **Нет риска нативной сборки.** `better-sqlite3` — нативный аддон;
   на конкретной версии Node/ОС хостинга для него может не найтись
   готового бинарника, и тогда потребуется `node-gyp` + компилятор.
   `node:sqlite` уже скомпилирован внутрь самого Node — собирать нечего.
3. **API synchronous**, как у `better-sqlite3` — `db.exec()`,
   `db.prepare(sql).run()/get()/all()`, транзакции через
   `db.exec('BEGIN')`/`COMMIT`/`ROLLBACK`. Ровно то, что нужно для
   миграций и сидов, где асинхронность только мешала бы.
4. Проверено вживую на установленной версии (Node 24.19.0): работает без
   флагов и без предупреждений об экспериментальности в stderr.

Если в будущем понадобится то, чего нет в `node:sqlite` (например,
пользовательские SQL-функции на JS или расширения SQLite), тогда стоит
пересмотреть выбор в пользу `better-sqlite3` — но добавлять его заранее,
про запас, не стали.

## 3. Нужная версия Node.js (важно для деплоя на BeGet)

**Жёсткий минимум: Node.js 22.5.0.** Модуль `node:sqlite` физически не
существует в более ранних версиях — на Node 18/20 (частый дефолт на
дешёвом виртуальном хостинге) `import('node:sqlite')` упадёт с
`ERR_MODULE_NOT_FOUND`.

Важно не путать этот порог с тем, что реально тестировалось: **22.5.0 —
это только документированный нижний порог**, ниже которого модуль
физически не существует, а не версия, на которой что-либо проверялось.
Вся разработка и все проверки в этом README фактически шли на
**Node 24.19.0** (актуальный LTS на момент написания) — именно её и
стоит ставить на BeGet, если нет отдельной причины использовать
конкретно линейку 22.x.

Что сделано, чтобы версия сервера не стала сюрпризом в момент деплоя:

- В `src/db/connection.js` — явная проверка версии перед любым
  обращением к БД. Если Node ниже 22.5.0, приложение падает сразу, с
  понятным сообщением на русском («обновите Node.js на сервере...»), а
  не с сырым стектрейсом где-то в середине запроса.
- Все npm-скрипты (`migrate`, `seed`, `db:reset`) запускают `node` с
  флагом `--experimental-sqlite`. На версиях 22.5–23.x этот флаг ещё
  обязателен; на более новых (включая 24.x) `node:sqlite` уже включён
  по умолчанию, и флаг — безопасный no-op (проверено: Node не отклоняет
  его как неизвестный).
- Если модуль всё равно не загрузился (например, кто-то запустил
  `node src/db/migrate.js` напрямую, в обход `npm run`, без флага) —
  тоже отдельное понятное сообщение с подсказкой, а не молчаливый сбой.

**Перед деплоем на BeGet:** зайти по SSH, выполнить `node --version`.
Если меньше 22.5.0 — обновить (через панель управления хостингом или
`nvm install --lts && nvm use --lts`, если есть доступ к nvm) **до**
первого запуска `npm run migrate` на сервере.

## 4. С какими сложностями столкнулись и как решили

Коротко и по делу — чтобы не наступать на те же грабли повторно.

- **`import.meta.url === 'file://' + process.argv[1]` не работает на
  Windows.** Абсолютный путь на Windows должен превращаться в
  `file:///C:/...` (три слэша), а простая конкатенация строк даёт
  `file://C:/...` (два) — сравнение никогда не совпадает, и код внутри
  `if` тихо не выполняется — без ошибки, без предупреждения. Из-за этого
  `migrate.js` сначала вообще не создавал таблицы, при этом завершался
  с кодом 0. Исправлено через `url.pathToFileURL(process.argv[1]).href`
  — это единственный надёжный способ сравнения такого рода, используйте
  его в любом новом скрипте с паттерном «выполняться только как main».

- **WAL/SHM-файлы SQLite не подпадают под маску `*.sqlite` в
  `.gitignore`.** Включили `journal_mode = WAL` — рядом с
  `database.sqlite` появляются `database.sqlite-wal` и
  `database.sqlite-shm`, у которых расширение не `.sqlite`, а
  `.sqlite-wal`/`.sqlite-shm`. Общие маски их не ловят. Решение — не
  городить ещё маски, а просто добавить в `.gitignore` весь каталог
  целиком: `/server/data/`.

- **Неизвестная версия Node.js на проде (BeGet).** См. раздел 3 —
  решили явной проверкой версии в коде плюс защитным флагом
  `--experimental-sqlite` во всех npm-скриптах, а не предположением,
  что на сервере окажется «достаточно новый» Node.

- **Момент создания записи не совпадает с моментом входа клиента.**
  При повторном разборе карты переходов прототипа обнаружилось: слот
  придерживается на шаге 3 («Дата и время»), а вход/регистрация — только
  на шаге 4. Первая версия схемы требовала `client_id NOT NULL`, что
  физически не соответствовало этому порядку экранов. Решение —
  `client_id` nullable + `hold_token` для анонимной идентификации до
  входа, подробный разбор альтернатив — в `docs/db-schema.md`, раздел
  «Спорные решения», пункт 12.

- **«Мастер» — не то же самое, что «пользователь с ролью мастер».**
  Формулировка задачи на сид тестовых данных подразумевала три роли
  (админ/мастер/клиент), а схема осознанно разделяет `users`
  (логин, роли `client`/`admin`) и `masters` (профиль без входа). Решение
  подтвердили с постановщиком задачи явно, а не выбрали молча — правку
  схемы под «мастер как роль» не делали, `masters` остаётся отдельной
  сущностью. Если это решение когда-то пересмотрят — правки нужны и
  здесь, и в `docs/db-schema.md` (раздел 3.6 и «Спорные решения»), и в
  миграции.

- **Хеширование пароля без внешних зависимостей.** Вместо `bcrypt`/
  `bcryptjs` — встроенный `node:crypto` (`scryptSync` +
  `timingSafeEqual`), вынесено в `src/security/passwords.js`. Формат
  хранимого значения — `scrypt:<соль-hex>:<хеш-hex>`, схема хеширования
  закодирована прямо в строке на случай, если её придётся сменить в
  будущем, не потеряв возможность проверять уже сохранённые пароли.
  Этот же модуль — переиспользовать в API аутентификации, когда он
  появится, а не писать хеширование заново.

- **Идемпотентность сида без ORM/upsert-логики.** `src/db/seed.js`
  просто удаляет управляемые им таблицы целиком и заново вставляет
  данные внутри одной транзакции — проще, чем возиться с `UPSERT`, и
  для dev-сида этого достаточно. Пока в проекте нет API регистрации,
  сиду разрешено удалять всю таблицу `users` целиком; как только
  появится реальная регистрация, это нужно будет сузить до «удалять
  только тестовых пользователей по email», иначе сид на дев-окружении
  будет стирать чужие тестовые аккаунты.

- **Правка одной защиты от двойной записи — не повод забыть остальные.**
  При добавлении `overlap_override` (миграция `003`) сначала поправили
  только триггер `trg_appointments_no_overlap_insert`, забыв, что
  `ux_appt_master_slot_active` — отдельный, самостоятельный механизм
  (раздел 6). Админ с `overlapOverride: true` получал не `201`, а те же
  `409` — ровно на самом частом случае наложения (совпадение времени
  старта), потому что индекс останавливал вставку раньше, чем до неё
  вообще доходило дело до триггера. Нашлось не чтением кода, а прогоном
  запроса через реальный HTTP API. Урок: когда «одна и та же гарантия»
  на самом деле реализована в нескольких независимых местах (индекс И
  триггер — оба про пересечение слотов, но разные механизмы БД), правка
  одного не гарантирует, что другой не откатит её эффект — проверять
  нужно результат сквозного запроса, а не то, что «нужный» кусок кода
  поправлен. Подробности — `docs/db-schema.md`, «Спорные решения», п.13.

## 5. Команды и карта файлов

Все команды — из папки `server/`:

```bash
npm run migrate    # применяет ещё не применённые миграции из src/db/migrations/
npm run db:reset   # удаляет файл БД (и -wal/-shm) и накатывает миграции с нуля
npm run seed       # наполняет базу тестовыми данными (идемпотентно)
```

`db:reset` и `seed` отказываются выполняться при `NODE_ENV=production` —
это защита от случайного запуска dev-скрипта на боевом сервере, а не
формальность.

```
server/
├── README.md                    # этот файл
├── .env.example                 # список нужных переменных окружения (реальный .env — в .gitignore)
├── package.json                 # без внешних зависимостей
├── data/                        # файл БД, создаётся автоматически, в .gitignore целиком
└── src/
    ├── config/env.js             # чтение .env, резолв пути к файлу БД
    └── db/
        ├── connection.js         # единственная точка открытия SQLite; проверка версии Node — здесь
        ├── migrate.js            # раннер миграций
        ├── reset.js              # пересоздание БД с нуля
        ├── seed.js                # тестовые данные для разработки
        └── migrations/            # 001_init.sql, 002_..., 003_... — правки схемы сначала
                                     вносятся в docs/db-schema.md, потом сюда
```

Остальной код (`http/`, `validation/`, `security/`, `time/`, `domain/`,
`middleware/`, `db/repositories/`, `routes/`, `app.js`, `index.js`) —
это уже HTTP API, отдельная карта файлов с пояснениями — раздел 6 ниже,
здесь не дублируется, чтобы не разъезжаться в двух местах при правках.

## 6. HTTP API — как устроен код в `src/`

API написан поверх `node:http` без фреймворка (без express) — тот же
принцип «ничего третьего», что и у слоя БД (раздел 2). Свой роутер —
`src/http/router.js`, статические сегменты и `:param`, без regex-магии
сверх необходимого.

Карта файлов:

```
src/
├── app.js                      # requestListener: роутинг + разбор тела +
│                                  пользователь из сессии + единая обработка ошибок
├── index.js                    # http.createServer + слушает PORT + фоновая
│                                  зачистка истёкших удержаний раз в минуту
├── http/                       # router, парсинг JSON-тела, cookies, ответы/ошибки
├── validation/validate.js      # все проверки входных данных — вызываются в
│                                  начале каждого маршрута, до обращения к БД
├── security/
│   ├── passwords.js            # (уже было) scrypt-хеширование
│   └── session.js              # подписанные сессионные токены, см. ниже
├── time/salonClock.js          # перевод локальное время салона <-> UTC (Intl,
│                                  без luxon/date-fns), используется и расчётом
│                                  слотов, и форматированием ответов
├── domain/
│   ├── availability.js         # расчёт свободного времени — раздел 5 db-schema.md
│   ├── holdExpiry.js           # истечение hold -> expired (лениво + по таймеру)
│   ├── holdAttach.js           # привязка анонимного hold_token к клиенту при входе
│   ├── booking.js              # создание hold/записи, перенос, отмена,
│   │                              защита от двойной записи (BEGIN IMMEDIATE)
│   └── appointmentView.js      # сборка ответа API по записи (UTC + локальное время)
├── middleware/auth.js          # пользователь из cookie, requireAuth/requireRole
├── db/repositories/            # тонкий SQL-слой поверх node:sqlite, по таблице на файл
└── routes/                     # auth, catalog (услуги/мастера), availability,
                                   holds, appointments, admin — по одному файлу на группу
```

**Сессии — без отдельной таблицы в БД.** В `docs/db-schema.md` нет
таблицы сессий, а заводить её в обход документа означало бы менять
схему по ходу задачи. Вместо этого `POST /api/auth/login` выдаёт
подписанный (HMAC-SHA256) токен без состояния на сервере — он лежит в
httpOnly-cookie и несёт `userId` + срок действия; `SESSION_SECRET` — в
`.env` (см. `.env.example`). Компромисс: `logout` снимает cookie у
клиента, но сам токен, если его успели скопировать, действителен до
истечения TTL — сервер не может его отозвать без собственного черного
списка/таблицы сессий. Для масштаба одного салона это осознанно принято;
если понадобится жёсткий отзыв — это отдельная таблица, значит и правка
`docs/db-schema.md`.

**Деньги — рубли, не копейки.** Сохранено ровно так, как в
`docs/db-schema.md` («Спорные решения», п.4): `price_rub` и производные
поля — целые рубли. API отдаёт и принимает суммы в тех же целых рублях
(поле называется `priceRub`), без домножения на 100 — намеренно, чтобы
не создавать формат, которого нет в хранимых данных.

**Защита от двойной записи** реализована в два слоя, как и предписано
документом схемы (раздел 4, «Спорные решения» п.1): явная проверка
пересечения диапазона в `src/domain/availability.js` внутри транзакции
`BEGIN IMMEDIATE` (см. `runOverlapProtectedInsert` в `booking.js`), и
частичный уникальный индекс `ux_appt_master_slot_active` — как
подстраховка на случай гонки за точное совпадение времени старта.
`node:sqlite` синхронный, поэтому между `BEGIN IMMEDIATE` и `COMMIT` в
коде нет ни одного `await` — событийный цикл Node физически не может
впустить туда параллельный запрос в рамках одного процесса.

**«Удаление» истёкших удержаний** (требование задачи) реализовано как
`status = 'expired'`, а не физический `DELETE FROM appointments` —
строки сознательно остаются для истории, это прямо описано в
`docs/db-schema.md` («Спорные решения», п.10). Смены статуса достаточно:
частичный уникальный индекс на слот действует только для
`hold`/`confirmed`, поэтому «удаление» здесь — это освобождение слота
для новой брони, а не стирание строки. Зачистка — лениво перед каждым
расчётом свободного времени/созданием брони, и дополнительно раз в
минуту фоновым таймером в `index.js`.

**CORS не настроен.** Фронтенда пока нет (см. ниже), поэтому
`Access-Control-Allow-Origin` и подобные заголовки не добавлялись —
добавить их нужно будет вместе с фронтендом, когда станет известен его origin.

**Восстановление пароля** (`domain/passwordReset.js`,
`POST /api/auth/password-reset/request` и `/confirm`) — реализовано
позже остального API, отдельным заходом: паспорт продукта прямо называет
эту функцию («Функция 1 … включая восстановление пароля»), но в
прототипе для неё нет экрана (`docs/db-schema.md`, «Спорные решения»,
п.8) — таблица `password_reset_tokens` была заведена заранее, логики не
было. Токен хешируется тем же способом, что и пароль пользователя
(`security/passwords.js`, scrypt) — искать его по значению напрямую
нельзя (хеш с солью не детерминирован), поэтому `confirm` принимает
`email` + `token` и ищет действующий токен по пользователю, а не по хешу
сразу. Одна проблема нашлась не в коде, а в самом паспорте: «Уведомления
приходят только внутри личного кабинета, интеграция с e-mail или
Telegram не входит в MVP» — а восстановление пароля по смыслу требует
канала **вне** личного кабинета (иначе замкнутый круг: чтобы увидеть
ссылку сброса, нужно быть залогинен). Решение, принятое явно с
постановщиком задачи: на время MVP `POST .../request` возвращает токен
прямо в теле ответа, а не отправляет его по почте — так функцию вообще
можно проверить и использовать без email-интеграции. Это осознанный
компромисс, а не то, как это должно работать в проде: токен в ответе
превращает «знание e-mail» в «может сбросить пароль этого аккаунта»,
теряя подтверждение владения почтой. Когда появится реальная
email/Telegram-интеграция — убрать `resetToken` из ответа и отправлять
токен по каналу; хранение и проверку токена трогать не придётся.

**Завершённые визиты и категории услуг** — закрывали не по прямому
запросу на фичу, а по собственному списку «осталось за рамками задачи»,
поэтому стоит явно пояснить, откуда они взялись:

- `status = 'completed'` теперь выставляется двумя путями — сразу оба, а
  не один на выбор, потому что документ схемы (`docs/db-schema.md`,
  раздел 6) описывает их через «или», не «либо-либо»: `POST
  /api/admin/appointments/:id/complete` (ручной, когда админу нужно
  закрыть визит раньше или без ожидания фоновой задачи) и
  `completePastAppointments` (`domain/completionSweep.js`) — тот же
  принцип ленивой зачистки, что и у `releaseExpiredHolds`: перед выдачей
  `GET /api/admin/appointments` и дополнительно раз в минуту фоновым
  таймером в `index.js`. На расчёт свободного времени смена `confirmed`
  → `completed` не влияет (прошедшие слоты и так не предлагаются) — это
  только гигиена данных для админ-панели.
- `service_categories` получили CRUD (`GET/POST/PATCH
  /api/admin/service-categories`) — раньше наполнялись только через
  `npm run seed`, и админ не мог завести новую категорию для новой
  услуги, не трогая код. Без hard-`DELETE` — как и у услуг/мастеров,
  сознательно только создание/переименование, потому что категория,
  на которую уже ссылаются услуги, не может быть физически удалена без
  `ON DELETE CASCADE`, которого в схеме нет намеренно (см.
  `docs/db-schema.md`, `services.category_id`).

## Дальше по проекту (пока не сделано)

Список того, что явно не входило в объём уже сделанной работы — чтобы
следующая сессия не искала это в коде и не считала упущением. Более
ранняя версия этого списка включала ещё «CRUD категорий услуг» и «перевод
записи в `completed`» — оба закрыты отдельным заходом (`domain/booking.js`,
`markAppointmentCompleted`; `domain/completionSweep.js`;
`routes/admin.routes.js`, `/api/admin/service-categories` и
`/api/admin/appointments/:id/complete`) и проверены вручную (ручное
завершение, повторное завершение уже завершённой записи, ленивая
зачистка прошедших визитов при обращении к списку). Осталось
по-настоящему не сделанным:

- Фронтенда нет — есть только статический прототип в `Full style guide
  DC/`, с бэкендом не связан. Не трогается сознательно — это отдельная
  задача, прямо исключённая из объёма текущей («фронтенд пока не
  собирай»).
- CORS не настроен — прямое следствие пункта выше: заголовки
  `Access-Control-Allow-Origin` настраиваются под конкретный origin
  фронтенда, а origin пока не существует. Настраивать «на всякий случай»
  под произвольный/угаданный origin — не защита, а бутафория; правильный
  момент для этого — когда появится сам фронтенд.
- Жёсткий отзыв сессий (server-side logout) — см. раздел 6 выше.
  Осознанный архитектурный компромисс, а не недосмотр: сессии сделаны
  без отдельной таблицы, потому что её нет в `docs/db-schema.md`, а
  завести такую таблицу — это уже правка документа схемы, а не
  доработка существующего кода. Если понадобится — начинать с
  `docs/db-schema.md`, не с кода.

При добавлении каждого из этих кусков — дополняйте разделы 1, 4 и 6
этого файла, не создавайте по новому документу на каждую фичу.
