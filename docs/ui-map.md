# Карта клиентских экранов

Собрано для передачи на вёрстку. Источники:

- прототип — папка [`Full style guide DC`](../Full%20style%20guide%20DC) (файлы `*.dc.html`, экспорт в `export/src/*.dc.html`);
- карта переходов — [`docs/Карта переходов прототипа.xlsx`](./Карта%20переходов%20прототипа.xlsx) (листы «Карта переходов» и «Нерешённые случаи»);
- API — код в [`server/src/routes`](../server/src/routes);
- для административных экранов (раздел 9 и далее) источник другой — см. оговорку перед разделом 9.

В прототипе нет папки с буквальным названием «Прототип» — экраны лежат в `Full style guide DC`, поэтому карта построена по ней.

**Клиентские экраны** (разделы 1–8): лендинг, авторизация внутри потока записи, сама запись, служебные экраны ошибок/успеха.

**Административные экраны** (разделы 9–15) добавлены отдельным заходом позже — карты для них в дизайн-прототипе нет вообще, источник другой (см. оговорку перед разделом 9).

Экраны мастера (`server/src/routes/master.routes.js`) по-прежнему не включены ни в каком виде — это ещё один будущий заход, для него пока нет даже черновой страницы.

**Важная оговорка**: экранов «Личный кабинет», «Профиль» и «Уведомления» в прототипе пока физически нет — их некуда поставить в таблицу. Это не недосмотр карты, а факт: лендинг, экран «Успех» и FAQ на лендинге ссылаются на личный кабинет и уведомления словами («запись появится в личном кабинете», «отменить можно в личном кабинете»), но соответствующих `.dc.html`-файлов не создавалось, а в «Карте переходов прототипа.xlsx» (лист «Нерешённые случаи», №2) это отмечено явно: переход с кнопки «В личный кабинет» не назначен, «такая страница не создавалась по условию задачи». Все связанные с этим эндпоинты API попали в список Б в конце документа.

Также не считаются экранами сценария: `Design my B.S..dc.html` (страница гайдлайна дизайн-системы) и `Canvas.dc.html` (пустой служебный холст) — это прямо оговорено в «Нерешённых случаях», №6.

## 1. Лендинг — `Landing my B.S..dc.html`

**Что показывает клиенту:** hero-блок с УТП и CTA «Записаться»; статичная trust-полоса (рейтинг 4.9, «2 400+ записей», «12 мастеров»); блок «Как это работает» (3 шага, текст); сетка услуг — 6 карточек (название, описание, длительность, цена, кнопка «Записаться»); сетка мастеров — топ-3 карточки (фото-плейсхолдер, имя, специализация, рейтинг, отзывы, «ближайшее окно», кнопка «Записаться»); демо-блок «Свободное время» (полностью статичный хардкод в коде компонента, не связан с реальными данными — только иллюстрация для лендинга); галерея «до/после», отзывы клиентов, FAQ (аккордеон) — весь контент статичный; футер с адресом/телефоном/соцсетями.

**Эндпоинты, дающие данные:** `GET /api/services` (карточки услуг), `GET /api/masters` (карточки мастеров — без поля «ближайшее окно», см. пробел А.1).

**Эндпоинты, которые вызывают кнопки:** ни один — все кнопки «Записаться» просто переводят на другой экран, API не дёргают. Кнопка «Войти» (шапка) тоже ничего не вызывает сама — переход есть (см. ниже), но это переход на страницу, не вызов API.

**Переходы:** 13 разных кнопок/карточек «Записаться» (шапка, hero, «Как это работает», карточки услуг, карточки мастеров, демо-слоты, финальный CTA) → **Booking · 1 · Услуги**. Кнопка «Войти» (шапка) — в прототипе перехода не было («Нерешённые случаи» №1), сейчас ведёт на отдельный экран входа `web/login.html` (свёрстан позже, вне карты прототипа — см. `web/README.md`). На `login.html` и на `web/register.html` рядом с обычной формой есть кнопка «Войти через Яндекс» — вход/регистрация в один клик через заглушку (`server/src/domain/yandexAuth.js`, приложение в настоящем Яндексе ещё не зарегистрировано, см. `server/README.md`).

## 2. Запись, шаг 1 — `Booking · 1 · Услуги.dc.html` (`booking-1.dc.html`)

**Что показывает клиенту:** степпер (1 из 4); табы категорий («Стрижка», «Окрашивание», «Уход», «Укладка»); сетку услуг выбранной категории с чекбоксом мультивыбора (название, описание, длительность, цена); нижнюю плашку со сводкой (кол-во услуг, суммарная длительность, сумма) и кнопками «Назад»/«Далее».

**Эндпоинты, дающие данные:** `GET /api/services` — карточки и группировка по категориям строятся из `categoryName`/`categoryId` в ответе.

**Эндпоинты, которые вызывают кнопки:** ни один — выбор услуг хранится только в состоянии экрана, к API на этом шаге не обращаются (фильтрация мастеров по набору услуг произойдёт на следующем шаге).

**Переходы:** «×» и «Назад» → **Landing my B.S.**; «Далее» (активна при ≥1 выбранной услуге) → **Booking · 2 · Мастер**.

## 3. Запись, шаг 2 — `Booking · 2 · Мастер.dc.html` (`booking-2.dc.html`)

**Что показывает клиенту:** степпер; баннер выбранных услуг со ссылкой «Изменить»; вариант «Любой свободный мастер» + карточки конкретных мастеров (фото, имя, специализация, рейтинг, отзывы, «ближайшее окно», ссылка «О мастере →»); три dev-состояния — обычное / скелетон загрузки / «никто не подходит».

**Эндпоинты, дающие данные:** `GET /api/masters?serviceIds=…` — уже возвращает только мастеров, которые могут выполнить **весь** набор выбранных услуг (пересечение `master_services` на бэкенде). Состояние «Никто не подходит» — это пустой массив в ответе.

**Эндпоинты, которые вызывают кнопки:** ни один — выбор мастера хранится в состоянии экрана до подтверждения записи.

**Переходы:** иконка «Услуги» в степпере, ссылка «Изменить», «Назад», «Изменить набор услуг» (состояние «Никто не подходит») → **Booking · 1 · Услуги**; «Далее» (активна при выбранном мастере) → **Booking · 3 · Дата и время**; «Записаться на две отдельные даты» (состояние «Никто не подходит») — переход не назначен (нет экрана под этот сценарий, «Нерешённые случаи» №4); ссылка «О мастере →» — целевого экрана нет ни в карте переходов, ни среди прототипов.

## 4. Запись, шаг 3 — `Booking · 3 · Дата и время.dc.html` (`booking-3.dc.html`)

**Что показывает клиенту:** степпер; баннер с выбранными мастером/услугами; календарь на месяц с маркерами «есть окно» / «окон нет» / «выходной» / прошедшая дата и навигацией на 3 месяца вперёд; сетку слотов (утро/день/вечер) на выбранный день; подсказку «мы придержим это время»; три dev-состояния — обычное / скелетон / «окон нет в этот день».

**Эндпоинты, дающие данные:** `GET /api/masters/:masterId/availability?date=…&serviceIds=…` — считает свободные слоты на **один конкретный день** под суммарную длительность услуг. Для маркеров календаря на весь месяц одного вызова недостаточно, см. пробел А.3.

**Эндпоинты, которые вызывают кнопки:** ни один напрямую по клику — выбор дня должен инициировать новый вызов `availability` для этого дня; выбор слота — только локальное состояние до перехода дальше.

**Переходы:** иконки «Услуги»/«Мастер» в степпере → соответствующие шаги; «Назад» → **Booking · 2 · Мастер**; «Далее» (активна при выбранном слоте) → **Booking · 4 · Вход в потоке**; «Показать других мастеров» (состояние «окон нет») — переход в карте не назначен.

## 5. Авторизация в потоке записи — `Booking · 4 · Вход в потоке.dc.html` (`booking-4.dc.html`)

**Что показывает клиенту:** степпер; баннер обратного отсчёта удержания слота (желтеет при <2 мин); сводку записи (полная карточка на десктопе / компактная строка на мобильном); вкладки «Войти» / «Создать аккаунт»; форму входа (e-mail, пароль, ссылка «Забыли пароль?»); форму регистрации (имя, e-mail, телефон, пароль, индикатор сложности пароля, чекбокс согласия с офертой); состояния ошибок («неверный e-mail или пароль», «e-mail уже занят»); экран «Время удержания истекло» с кнопками «Вернуть 14:00» / «Выбрать другое время».

**Эндпоинты, дающие данные:** таймер удержания на этом экране должен отражать `holdExpiresAt` из ответа `POST /api/holds`, полученного ещё на шаге 3.

**Эндпоинты, которые вызывают кнопки:** «Войти» → `POST /api/auth/login` (тело поддерживает `holdToken` — API сам привяжет анонимное удержание к вошедшему клиенту, `attachClientToHold`); «Создать и продолжить» → `POST /api/auth/register` (тоже принимает `holdToken`, `termsAccepted` — чекбокс оферты обязателен и на бэкенде); «Забыли пароль?» — на бэкенде под это есть `POST /api/auth/password-reset/request` и `POST /api/auth/password-reset/confirm`, но у ссылки нет ни экрана, ни перехода в прототипе (см. пробел Б.6); «Вернуть 14:00» — прямого эндпоинта «продлить удержание» нет, по факту это должен быть новый `POST /api/holds`.

**Переходы:** иконки шагов «Услуги»/«Мастер»/«Время» в степпере → соответствующие шаги; «Войти» / «Создать и продолжить» (переход через ~0.9 с имитации загрузки) → **Booking · 5 · Подтверждение**; «Выбрать другое время» (экран «Время истекло») → **Booking · 3 · Дата и время**; «Забыли пароль?» — переход не назначен (страницы восстановления пароля в прототипе нет, «Нерешённые случаи» №3).

## 6. Подтверждение — `Booking · 5 · Подтверждение.dc.html` (`booking-5.dc.html`)

**Что показывает клиенту:** степпер; баннер таймера удержания; предупреждение о пересечении с уже существующей записью клиента (dev-переключатель); карточку записи (дата/время, мастер, список услуг с ценами, итоговая сумма и длительность, «оплата в салоне», адрес салона); поле комментария мастеру со счётчиком символов (0/200); чекбокс «Напомнить мне о визите»; CTA «Записаться».

**Эндпоинты, дающие данные:** сама карточка — это данные, накопленные на шагах 1–4 (мастер, услуги, слот), отдельного `GET` не требует. Адрес/название/телефон салона в карточке сейчас захардкожены — публичного эндпоинта для них нет (пробел А.4). Предупреждение «У вас уже есть запись…» по смыслу требует `GET /api/appointments` для текущего клиента — в прототипе не описано, в какой момент шага этот вызов должен происходить (пробел А.5).

**Эндпоинты, которые вызывают кнопки:** «Записаться» → `POST /api/appointments` — поля экрана совпадают с телом запроса один в один: `holdToken` (из шага 3), `comment` (из текстового поля, лимит 200 знаков на бэкенде совпадает с UI), `remindEnabled` (чекбокс). Ссылки «Изменить» — переход назад, API не вызывают.

**Переходы:** иконки шагов в степпере и ссылки «Изменить» (дата/время, мастер, услуги) → соответствующие шаги; «Записаться» (переход через ~0.9 с) → **Booking · 6 · Успех**.

## 7. Успех — `Booking · 6 · Успех.dc.html` (`booking-6.dc.html`) — служебный экран

**Что показывает клиенту:** подтверждение «Вы записаны»; карточку записи (дата/время, мастер, услуги, длительность, сумма, адрес салона); текст «Уведомление о записи придёт в личный кабинет»; кнопки «В личный кабинет» и «Добавить в календарь»; ссылку «Записаться ещё раз».

**Эндпоинты, дающие данные:** карточка — это тот же объект `appointmentView`, который вернул `POST /api/appointments` на предыдущем шаге (поля `startLocal`, `master`, `services`, `totalPriceRub`, `totalDurationMinutes` совпадают один в один). Фраза про уведомление в личном кабинете не подкреплена API — ни таблицы, ни эндпоинта уведомлений в проекте нет (пробел А.6).

**Эндпоинты, которые вызывают кнопки:** ни один напрямую — «Добавить в календарь» обычно реализуется экспортом `.ics` на фронте, отдельного эндпоинта не требует.

**Переходы:** «В личный кабинет» — переход не назначен (страницы личного кабинета не существует, «Нерешённые случаи» №2); «Записаться ещё раз» → **Booking · 1 · Услуги**.

## 8. Служебный экран — `Ошибка · Слот занят.dc.html` (`error-slot-taken.dc.html`), полноэкранный и модальный варианты

**Что показывает клиенту:** сообщение «Это время только что заняли»; три альтернативных слота у того же мастера; кнопку «Выбрать другое время»; ссылку «14:00 свободно у другого мастера»; напоминание, что выбранные услуги сохранены. Модальный вариант — то же самое поверх затемнённого экрана подтверждения (переключается dev-кнопкой, не отдельным переходом).

**Эндпоинты, дающие данные:** экран — это реакция на конфликт при бронировании (`POST /api/holds` или `POST /api/appointments` возвращает ошибку конфликта, если слот заняли за это время); альтернативные слоты — повторный вызов `GET /api/masters/:masterId/availability` на ту же дату.

**Эндпоинты, которые вызывают кнопки:** выбор альтернативного слота — локальное состояние; «Выбрать другое время» и ссылка «…у другого мастера» — переходы, API не вызывают напрямую.

**Переходы:** «Выбрать другое время» → **Booking · 3 · Дата и время**; «14:00 свободно у другого мастера» → **Booking · 2 · Мастер**. Входящего перехода на этот экран в карте намеренно нет — по «Нерешённым случаям» №5, конфликт разыгран как состояние самих экранов шага 3/5 через dev-переключатели, а не как переход с кнопки.

## Административные экраны

**Важная оговорка про источник.** В папке прототипа (`Full style guide DC`) административных `.dc.html`-экранов нет ни одного — там только 6 шагов записи, лендинг, `Ошибка · Слот занят`, `Design my B.S.` и `Canvas`. По решению, принятому при составлении этого раздела, вместо прототипа за источник взята страница [`frontend/public/admin.html`](../frontend/public/admin.html) (и её скрипт [`frontend/public/js/admin.js`](../frontend/public/js/admin.js)) — черновой тестовый фронт из коммита «Тестовый фронтенд и исправление уязвимости восстановления пароля», а не дизайн-прототип. Отсюда два следствия:

- Это **одна физическая HTML-страница**, поделённая на разделы якорями (`#appointments`, `#salon`, `#categories`, `#services`, `#masters`, `#users`) — правило «один экран прототипа — одна страница» (`docs/frontend-rules.md`, п. 2) в этом источнике не соблюдено изначально. Ниже каждый раздел всё равно описан отдельной строкой, по аналогии с клиентскими экранами, но переходы между ними — это прокрутка по якорю внутри одной страницы, а не переход на другой файл.
- У административных «экранов» нет макета/вёрстки для ориентира — только голые HTML-формы и таблицы с текстовыми подсказками вида `GET /api/admin/...` прямо в разметке. Расположение полей и порядок элементов ниже описаны по факту разметки `admin.html`, это не дизайнерское решение.

Экраны роли **мастер** (`server/src/routes/master.routes.js`) в этот заход не входят — для них нет ни дизайн-прототипа, ни черновой страницы вроде `admin.html`.

## 9. Все записи (администратор) — `frontend/public/admin.html#appointments`

**Что показывает администратору:** таблицу всех записей салона (колонки: ID, статус, клиент, мастер, время, сумма, ссылка «Подробнее →») с формой фильтра (статус, ID мастера, ID клиента, диапазон дат); форму «Завершить визит вручную» (ID записи); форму «Ручное бронирование администратором» (ID клиента, ID мастера, ID услуг через запятую, начало в UTC ISO, комментарий, чекбоксы «Напоминание включено» и «Осознанное наложение (overlapOverride)»).

**Эндпоинты, дающие данные:** `GET /api/admin/appointments?status=&masterId=&clientId=&from=&to=` — список подгружается автоматически при открытии страницы (без фильтров) и повторно при отправке формы фильтра.

**Эндпоинты, которые вызывают кнопки:** «Показать» → тот же `GET /api/admin/appointments` с параметрами формы; «Завершить» → `POST /api/admin/appointments/:id/complete` (после успеха список перезагружается); «Создать запись» → `POST /api/admin/appointments` — единственный маршрут, где можно осознанно забронировать поверх занятого времени тем же мастером (`overlapOverride`); после успеха форма сбрасывается и список перезагружается.

**Переходы:** ссылка «Подробнее →» у каждой строки ведёт на `frontend/public/account.html?id=<id>` — это клиентский экран «Личный кабинет» того же тестового фронта, не отдельный админский экран. Там уже реализованы просмотр деталей записи (`GET /api/appointments/:id`), перенос (`PATCH /api/appointments/:id/reschedule`, с полем смены мастера — «менять может только admin», прямо написано в подсказке на экране) и отмена (`POST /api/appointments/:id/cancel`) — то есть эти три эндпоинта администратор использует через общий с клиентом экран, отдельного экрана под них в `admin.html` нет. Пункты навигации `#salon`/`#categories`/`#services`/`#masters`/`#users` в шапке страницы — прокрутка к другим разделам той же страницы.

## 10. Профиль салона — `frontend/public/admin.html#salon`

## Что на стороне экрана решить нельзя

Без изменений в `server` эти три вещи так и останутся ограничениями — называю их, ничего не предлагая взамен:

- **Полноценные уведомления** (не только фраза на экране «Успех», а сама функция) — в БД и API нет ни хранилища, ни одного эндпоинта под события уведомлений; собрать их из существующих ручек нечем.
- **Быстрый расчёт «ближайшего окна» мастера и доступности на весь месяц** — решения А.2 и А.3 работают только за счёт множества последовательных запросов к `GET /api/masters/:id/availability`; агрегирующего эндпоинта, который отдавал бы это одним запросом, нет, и обойти это на экране без потери скорости нельзя.
- **Публичные и всегда актуальные данные о салоне** — решение А.4 фиксирует адрес/телефон/часы работы как текст в вёрстке; если администратор поменяет их через `PATCH /api/admin/salon-profile`, клиентский экран этого не узнает, потому что публичного эндпоинта для чтения этих данных нет.

## В. Административные экраны, которым не хватает данных в API

Не найдено ни одного. Все разделы `admin.html` (9–15) построены по тем же эндпоинтам `/api/admin/...`, которые их и обслуживают, — данных для полей и таблиц хватает везде.

## Г. Административные эндпоинты, для которых не нашлось экрана

Среди 25 маршрутов `server/src/routes/admin.routes.js` не найдено ни одного, для которого нет ни поля, ни кнопки в `admin.html` — все они использованы в разделах 9–15 выше.

Отдельно, за пределами `admin.routes.js`, есть три маршрута из `server/src/routes/appointments.routes.js`, которые администратору доступны по роли (`assertCanAccessAppointment`/`assertCanModifyAppointment` в этом файле явно разрешают роль `admin`), но собственного экрана в `admin.html` под них нет — администратор пользуется тем же экраном, что и клиент (`frontend/public/account.html`, раздел «Детали записи», см. переходы у раздела 9 выше):

- `GET /api/appointments/:id` — детали одной записи (с `includeClient: true` для админа/мастера);
- `PATCH /api/appointments/:id/reschedule` — перенос записи, включая смену мастера (`newMasterId`), которую могут выполнять только администраторы;
- `POST /api/appointments/:id/cancel` — отмена записи.

Это не совсем «эндпоинт без экрана» — экран есть, просто общий с клиентом, а не отдельный административный, и попасть на него администратор может только по ссылке «Подробнее →» из раздела 9 или вручную открыв `account.html?id=…`.
