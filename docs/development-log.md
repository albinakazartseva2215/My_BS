# Журнал разработки — исправление находок ручной проверки

Источник находок — [`docs/test-checklist.md`](./test-checklist.md), составленный
самостоятельным прогоном сервиса. Ниже — что было сломано в каждой находке
Группы 1 и Группы 2, в чём была причина и как это исправлено. Каждая правка
проверялась вручную (curl/браузер) на самом сценарии находки и на соседних
сценариях, которые могла задеть правка; тестовые данные после проверки
удалены.

---

## Группа 1 — портили данные

### Находка 1. Перенос записи на другого мастера не проверял, что новый мастер выполняет услугу записи

**Что было сломано:** перенос подтверждённой записи на мастера, который
физически не выполняет её услугу(и), проходил успешно (`200`) — запись
переезжала к мастеру вместе с услугой, которую он не делает.

**Причина:** `rescheduleAppointment` (`server/src/domain/booking.js`)
вызывала `getActiveMasterOrThrow(masterId)` и `assertSlotBookable(...)`, но не
`masterCanPerformAllServices` — эта проверка существовала только внутри
`resolveServicesOrThrow`, которую использует `createAppointment`;
`rescheduleAppointment` её не вызывала вовсе.

**Как исправлено:** в `rescheduleAppointment` добавлена проверка
`masterCanPerformAllServices(masterId, serviceIds)` (услуги записи —
через `listAppointmentServices`) сразу после `getActiveMasterOrThrow`, с тем
же текстом ошибки, что и при создании записи. Перенос на мастера, который не
выполняет хотя бы одну услугу записи, теперь отклоняется `400`.

---

## Группа 2 — мешали пользоваться сервисом

### Находка 3. Выходной день/блокировка времени не видели существующую запись

**Что было сломано:** можно было пометить день выходным или поставить ручную
блокировку времени поверх уже подтверждённой записи клиента без единого
предупреждения — запись оставалась «подтверждённой», но расчёт доступности
показывал это время как недоступное, как будто записи не существует.

**Причина:** ни `POST .../schedule-exceptions`, ни `POST .../time-blocks`
(`server/src/routes/admin.routes.js`) не сверялись с таблицей `appointments`
перед сохранением.

**Как исправлено:** перед сохранением обоих типов блокировки добавлена
проверка активных (`hold`/`confirmed`) записей мастера, пересекающихся по
времени с новым диапазоном — новая функция
`listActiveAppointmentsInRange` (`server/src/db/repositories/appointments.js`,
аналог уже существующей `findAppointmentsOverlapping`, но без исключения
«самой себя», так как блокировка не привязана к конкретной записи). При
конфликте сервер отвечает `409` со списком `appointmentIds`, ничего не
сохраняя.

### Находка 2. Текст уведомления о переносе не различал «сменился мастер» и «перенос на ту же комбинацию день+время через N недель»

**Что было сломано:** оба случая давали один и тот же бессмысленный текст
«Запись на среду, 12:00 перенесена на среду, 12:00.» — клиент не мог понять,
что вообще изменилось.

**Причина:** `formatDayTime`/`notifyIfAppointmentRescheduledByOther`
(`server/src/domain/notifications.js`) кодировали и сравнивали только день
недели и время суток — не полную дату и не мастера.

**Как исправлено:** добавлена `formatDayDateTime` (день недели + число +
месяц + время) и явное сравнение `oldMasterId`/`newMasterId`, переданных из
`booking.js`. Текст теперь собирается по тому, что реально изменилось: смена
времени, смена мастера или оба сразу — с полной датой и, при смене мастера,
именами обоих мастеров.

### Находка 4. Форма создания записи не фильтровала услуги по мастеру

**Что было сломано:** список чекбоксов услуг в форме «Создать запись»
показывал все активные услуги независимо от выбранного мастера; ошибка
всплывала только после отправки формы.

**Причина:** `servicesCheckboxesHtml` (`web/js/admin-appointments.js`)
строила список один раз при загрузке страницы из полного каталога услуг и не
обновлялась при смене мастера в соседнем `<select>`.

**Как исправлено:** `servicesCheckboxesHtml` теперь принимает `masterId` и
фильтрует услуги по `master.serviceIds`; добавлен обработчик `change` на
выбор мастера, перерисовывающий список чекбоксов.

### Находка 5. Услугу/мастера с любой историей нельзя было удалить физически

**Разбор показал, что это не баг, а два намеренных уровня защиты:**
`countAppointmentServicesForService`/`countAppointmentsForMaster` считают всю
историю без фильтра по статусу, и вдобавок сама БД блокирует физическое
удаление через внешний ключ без `ON DELETE`, пока существуют записи
`appointment_services`/`appointments`, ссылающиеся на строку (а они не
удаляются физически никогда — осознанное архитектурное решение,
`docs/db-schema.md`, «Спорные решения», п.10). Проверено вживую тестовой
транзакцией: даже при обходе проверки на уровне приложения `DELETE` падает с
`FOREIGN KEY constraint failed`.

**Решение:** после совместного разбора поведение признано верным как есть —
правка не вносилась. Услуга/мастер с любой историей (включая отменённую)
по-прежнему отключается, а не удаляется физически.

## Косметические недочёты — остаются в отдельном списке (не исправлялись)

Смотри [`docs/test-checklist.md`](./test-checklist.md), группа 3:

- **№6** — форма отмены записи обещает клиенту показать причину отмены
  («видна клиенту»), но ни один клиентский экран пока не выводит
  `cancelReason`/`cancelledBy` из ответа API.
- **№7** — дата уведомления на `account-notifications.html` показывается без
  года («10 сентября в 20:45»).
