# Вёрстка клиентских экранов

Обычный HTML/CSS/JS без сборщиков (docs/frontend-rules.md). Один экран
прототипа — одна страница здесь.

## Запуск

Бэкенд должен быть уже поднят (из `server/`):

```bash
npm run migrate
npm run seed
npm start
```

Затем сам лендинг (из `web/`):

```bash
npm start
```

Откройте <http://localhost:5174>. `server.js` — маленький dev-сервер без
зависимостей: раздаёт статику из этой папки и проксирует всё под `/api/*`
на бэкенд (порт 3000 по умолчанию, переопределяется `API_ORIGIN`; порт
самого лендинга — `WEB_PORT`, по умолчанию 5174). Тот же приём, что уже
используется в `frontend/server.js`.

## Файлы

- `index.html` — лендинг (Full style guide DC/export/src/landing.dc.html).
- `tokens.css` — токены дизайн-системы (цвета, шрифты, размеры, отступы).
- `css/base.css` — общий сброс, типографика, кнопки, контейнер — то, что
  переиспользуют будущие страницы.
- `css/landing.css` — стили, специфичные для лендинга.
- `css/auth.css` — стили входа/регистрации/восстановления пароля.
- `css/account.css` — стили личного кабинета и деталей записи (см. шапку
  файла — источники по секциям Design my B.S..dc.html).
- `css/booking.css` — стили визарда записи (Booking · 1, · 2 и далее).
- `js/api.js` — единственное место обращения к серверу (правило 3).
- `js/routes.js` — адреса переходов между экранами по `docs/ui-map.md`.
- `js/format.js` — форматирование цены/длительности/инициалов, общее для
  нескольких экранов.
- `js/forms.js` — общие помощники форм входа/регистрации.
- `js/header.js` — общая шапка сайта (лого, разделы, вход/аватар, бургер).
- `js/nav.js` — мобильное меню шапки.
- `js/store.js` — состояние визарда записи (услуги/мастер/слот/удержание/
  последняя оформленная запись) в sessionStorage — единственное место,
  которое туда пишет и читает.
- `js/booking-flow.js` — мини-шапка визарда (лого + крестик) и степпер,
  общие для Booking · 1–4 (у Booking · 5 · Успех своей шапки визарда нет).
- `js/dates.js` — календарные хелперы (месяцы, "сегодня/завтра", сетка
  месяца), общие для Booking · 3 и личного кабинета.
- `js/landing.js` — логика лендинга: рендер услуг/мастеров из API,
  декоративные куски прототипа (демо-слоты, FAQ), навигация.
- `login.html`/`js/login.js`, `register.html`/`js/register.js`,
  `password-reset.html`/`js/password-reset.js` — вход, регистрация,
  восстановление пароля.
- `account.html`/`js/account.js` — личный кабинет: список записей с
  вкладками «Активные»/«История» (ближайший активный визит подсвечен),
  пустой кабинет — состояние того же списка (текст и кнопка «Записаться»
  дословно из Design my B.S..dc.html, секция "07 · Обратная связь").
  Прототипового экрана-образца нет — «Нерешённые случаи», №2
  (docs/ui-map.md); источники вида — см. шапку `css/account.css`.
- `account-appointment.html`/`js/account-appointment.js` — детали записи:
  карточка визита, «Отменить» (модалка с текстом о правилах отмены и
  предупреждением, если до визита осталось меньше 2 часов) и «Перенести»
  (ведёт на `booking-3.html?reschedule=<id>`).
- `booking-1.html`/`js/booking-1.js` — Booking · 1 · Услуги: мультивыбор
  услуг, сумма/длительность внизу — из объектов `GET /api/services`
  (см. комментарий в начале `js/booking-1.js` про пробел с агрегирующим
  эндпоинтом).
- `booking-2.html`/`js/booking-2.js` — Booking · 2 · Мастер: список
  мастеров под выбранные услуги (`GET /api/masters?serviceIds=…`),
  неподходящие — неактивны с пояснением.
- `booking-3.html`/`js/booking-3.js` — Booking · 3 · Дата и время:
  календарь месяца (статус каждого дня — свой вызов
  `GET /api/masters/:id/availability`) и сетка слотов на выбранный день
  (`allSlots` из того же ответа — свободные/занятые/прошедшие, занятые
  показаны, а не спрятаны); нет окон в этот день — состояние того же
  экрана с ближайшим свободным временем. «Любой свободный мастер» с
  Booking · 2 разрешается здесь в конкретного мастера (см. комментарий в
  начале `js/booking-3.js`). Тот же экран умеет режим переноса записи из
  личного кабинета (`?reschedule=<id>`) — мастер и услуги зафиксированы
  (берутся из самой переносимой записи), старое время показано отдельной
  строкой в баннере и кольцом на календаре; отправка —
  `PATCH /api/appointments/:id/reschedule`, а не создание новой записи.
- `booking-4.html`/`js/booking-4.js` — Booking · 4 · Подтверждение (+ вход):
  слева форма входа/регистрации (или заметка "вы вошли", если сессия уже
  есть), справа сводка визита с итогом и ссылками «Изменить»; на входе на
  экран создаёт удержание слота (`POST /api/holds`) и считает от него
  таймер, предупреждает видом при <60 с; «Подтвердить запись» при
  необходимости входит/регистрируется, затем подтверждает удержание
  (`POST /api/appointments`). Пояснение, почему прототиповские «Booking · 4 ·
  Вход» и «Booking · 5 · Подтверждение» здесь — один экран, и откуда
  сдвиг номеров в именах файлов — в комментарии у `BOOKING_CONFIRM_URL`
  (`js/routes.js`) и в начале `js/booking-4.js`. 409 «слот заняли» (на
  удержании или на подтверждении) — состояние того же экрана (Booking 04b):
  текст из ответа сервера, кнопки ближайших слотов из `err.details.nearbySlots`,
  ссылка на выбор другого времени.
- `booking-5.html`/`js/booking-5.js` — Booking · 5 · Успех (прототиповский
  «Booking · 6»): карточка — тот же объект, что вернул
  `POST /api/appointments` на предыдущем шаге, без отдельного `GET`;
  «Добавить в календарь» — `.ics`-файл собирается на фронте.

### Административный раздел (`/admin`)

Состав — по `docs/ui-map.md`, разделу «Административные экраны»: там же
оговорено, что источник не дизайн-прототип (в нём административных экранов
нет вообще), а черновой тестовый фронт `frontend/public/admin.html`. Пока
только каркас — три пустых раздела без данных.

- `admin/index.html` (`/admin`), `admin/services.html` (`/admin/services`),
  `admin/masters.html` (`/admin/masters`) — «Записи», «Услуги», «Мастера»;
  каждая страница — только заголовок и заглушка "раздел пока без данных".
- `admin/403.html` — «Этот раздел только для администраторов». Напрямую не
  открывается: сервер (`server.js`, см. ниже) сам подставляет её с кодом
  ответа 403 вместо любой страницы `/admin*`, если у вошедшего нет роли
  `admin` (или он не вошёл вовсе).
- `js/admin-shell.js` — общий каркас (шапка + меню трёх разделов) для всех
  страниц `/admin`, тот же приём, что и `js/header.js` для клиентской
  шапки; `js/admin-appointments.js`, `js/admin-services.js`,
  `js/admin-masters.js` — по одному вызову `initAdminShell()` на страницу.
- `css/admin.css` — стили раздела, переиспользует `.site-header` и `.btn`
  из `css/base.css`, новых цветов/шрифтов/размеров не заводит (правило 4).
- `js/routes.js` — добавлены адреса `/admin`, `/admin/services`,
  `/admin/masters` (абсолютные, не относительные, — см. комментарий в
  файле: страницы `/admin/*` лежат на разной "видимой" глубине URL).
- `js/login.js` — форма входа общая для клиента и администратора; после
  входа адрес личного кабинета выбирается по ролям пользователя из ответа
  сервера (`user.roles.includes('admin')`).
- `js/header.js` — пункт «Админ-панель» в шапке показывается только когда
  у вошедшего есть роль `admin`; это не защита, а декорация (см. ниже).
- `server.js` — сюда же добавлена сама проверка доступа: для любого пути
  `/admin` или `/admin/*` сервер сам спрашивает у бэкенда
  `GET /api/auth/me` (с теми же cookie, что пришли в запросе браузера) и,
  если роли `admin` нет, отдаёт `admin/403.html` с HTTP 403 вместо файла
  страницы — раньше, чем страница вообще дошла бы до браузера. Это
  отдельная, вторая линия защиты: каждый административный эндпоинт
  бэкенда закрыт независимо от неё, на самом API
  (`server/src/routes/admin.routes.js`, `requireRole(ctx, 'admin')`).
